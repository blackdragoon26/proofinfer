KV-cache, weight-slice, and Q8_0 index safety in Verus

This directory holds a machine-checked proof of the property named in CONTEXT.md section 10, question 7: KV-cache and attention indexing never goes out of bounds for any pos < seq_len, extended to cover State::new's checked cache-length arithmetic, parametric Weights::layer slicing, and Q8_0 quantized block and scale indexing (dot_q80 and matmul_q80).

  • kv_cache_bounds.rs — the Verus development. 46 verification conditions, all discharged by Verus under --no-cheating. See "Verification status" below for the exact command and its real output.
  • check_citations.py — bidirectional, symbol-scoped citation verifier tying this document and kv_cache_bounds.rs to src/ops.rs and src/model.rs.
  • This page — what is proved, where it lands in the Rust source, what is not proved, and how to re-run the check.

1. The property, precisely

The shapes. n_layers, n_heads, n_kv_heads, head_size, seq_len are integers, and kv_dim = head_size * n_kv_heads and kv_layer_stride = seq_len * kv_dim. The KV cache is n_layers * kv_layer_stride floats, so layer l occupies [l * kv_layer_stride, (l + 1) * kv_layer_stride).

The structural preconditions, transcribed from the checks the loader actually performs: n_layers > 0, n_heads > 0, n_kv_heads > 0, seq_len > 0, head_size > 0, and n_heads % n_kv_heads == 0.

Claim 1 — the shapes and checked cache bounds follow from the loader and State::new. lemma_shapes_from_config shows that anything passing model.rs::Config::validate and ops.rs::AttentionDims::try_new yields a shape tuple satisfying the preconditions above. The only non-obvious part is head_size > 0, which the loader never checks explicitly: it computes head_size = dim / n_heads only after rejecting dim == 0 and dim % n_heads != 0, and a divisor of a positive number is positive. lemma_kv_dim_le_dim proves head_size * n_kv_heads <= dim <= usize::MAX from those same checks, and exec_checked_cache_len proves that model.rs::State::new's checked_mul chain plus isize::MAX byte-capacity bound guarantees seq_len * kv_dim <= usize::MAX, n_layers * (seq_len * kv_dim) <= usize::MAX, and cache * 4 <= isize::MAX.

Claim 2 — the attention read is in bounds (lemma_attention_row_in_layer). For every t with 0 <= t <= pos and every kv with kv < n_kv_heads:

t*kv_dim + kv*head_size  <  t*kv_dim + (kv+1)*head_size  <=  (pos+1)*kv_dim  <=  kv_layer_stride

That is: the half-open range [t*kv_dim + kv*head_size, t*kv_dim + (kv+1)*head_size) is non-empty and lies inside the pos + 1 live rows, hence inside the layer. Supporting facts: lemma_limit_rows_fit_in_layer (the pos + 1 live rows fit in a layer, because pos < seq_len) and lemma_gqa_head_in_range (kv = h / kv_mul is in 0..n_kv_heads for h < n_heads).

Claim 3 — the per-layer write is in bounds (lemma_cache_write_in_cache). For every l < n_layers and pos < seq_len:

l*kv_layer_stride + pos*kv_dim + kv_dim  <=  cache_len
l*kv_layer_stride + pos*kv_dim + kv_dim  <=  l*kv_layer_stride + kv_layer_stride

The second is what makes the attention read immediately afterwards observe the value just written. Supporting fact: lemma_layer_slice_in_cache, the per-layer slice [l*stride, l*stride + stride) is inside the whole cache.

Claim 4 — end-to-end forward to attention composition (lemma_attention_row_in_cache and exec_forward_cache_write_and_layer_slice). At the proof level, lemma_attention_row_in_cache folds the layer offset into the attention bound. At the executable Rust level, exec_forward_cache_write_and_layer_slice slices &key_cache[layer_start..layer_end] and &value_cache[layer_start..layer_end] and passes them directly into exec_attention_read, so Verus machine-checks that the per-layer slice satisfies attention's preconditions.

Claim 5 — the remaining attention scratch slices. lemma_query_head_in_q (&q[h*head_size..(h+1)*head_size] and &mut out[h*head_size..(h+1)*head_size] in ops.rs::attention) and lemma_scores_window_in_scratch (&mut scores[..limit] in ops.rs::attention).

Claim 6 — parametric per-layer weight slicing (lemma_layer_tensor_slice and exec_weight_layer_slice). For any per-layer weight tensor of length n_layers * per_layer and any layer l < n_layers, model.rs::Weights::layer's slice &buf[start..start + per_layer] (where start = l * per_layer) is non-empty, overflow-free, and in bounds. This covers all nine per-layer weight accessors (rms_att, rms_ffn, wq, wk, wv, wo, w1, w2, w3) uniformly.

Claim 7 — Q8_0 quantized block and scale indexing (lemma_q80_groups_tile_dim, lemma_q80_group_slice_in_row, lemma_q80_row_and_scale_in_matrix, exec_q80_dot_bounds, and exec_q80_matmul_bounds). For any d > 0, group_size > 0 with d % group_size == 0, every i8 block slice &w.q[start..end] and &x.q[start..end] and every per-group scale access w.s[g] / x.s[g] in ops.rs::dot_q80 is non-empty, overflow-free, and in bounds; and exec_q80_matmul_bounds composes the row/scale slicing in ops.rs::matmul_q80 directly into exec_q80_dot_bounds.

3. What is inside the lemma, and what is not

Inside.

  • The bounds of every KV-cache index expression, for all shapes satisfying the structural preconditions and all pos < seq_len.
  • That those structural preconditions and kv_dim <= dim <= usize::MAX follow from the conditions the loader checks (transcribed by hand — see below).
  • That State::new's checked_mul + isize::MAX byte-capacity guard prevents usize and allocation-size overflow for the KV cache (exec_checked_cache_len).
  • That the composed forward -> attention slice handoff satisfies attention's buffer-length preconditions (exec_forward_cache_write_and_layer_slice calling exec_attention_read directly on &[f32] layer slices).
  • That Weights::layer's slice &buf[start..start + per_layer] is in bounds and overflow-free for all l < n_layers (exec_weight_layer_slice).
  • That the GQA head mapping h / kv_mul lands inside 0..n_kv_heads.
  • That the index arithmetic cannot overflow usize, both via Verus's own no-overflow check on the real slices and via the explicit lemma_index_fits_in_usize.

Outside. None of the following is proved, and nothing here should be read as claiming otherwise.

  1. This is not a verification of the crate. src/ops.rs and src/model.rs contain no verus! macro and are not compiled by Verus. The development is a separate model file. To verify the crate itself you would need vargo and to annotate the real functions; that was not attempted so the crate keeps zero external dependencies and Rust 1.70.0 MSRV.
  2. The correspondence between the model and the code is manual, bounded by a syntactic citation check. The Shapes preconditions and the exec fn bodies were transcribed by a human. verus/check_citations.py closes the syntactic drift mode on both sides: it tokenizes Rust code (skipping // and nested /* ... */ comments, treating string literals as atomic tokens so string text cannot satisfy a code check, and matching on full token boundaries), resolves each symbol cited in this file and in kv_cache_bounds.rs, asserts every required token sequence (including full lower and upper slice bounds, checked_mul chains, Weights::layer, and the composed exec_attention_read call) appears in src/ and in the paired exec_* body in verus/kv_cache_bounds.rs, and runs --self-test in CI to prove mutations on either side fail. What that check does not do is verify semantic equivalence across un-cited code: an edit that preserves a cited expression's tokens while altering how variables are initialized elsewhere would still pass.
  3. Checkpoint tensor-table try_fold arithmetic is still assumed. State::new's checked_mul + isize::MAX byte-capacity check and kv_dim <= dim are now proved (exec_checked_cache_len, lemma_kv_dim_le_dim), but model.rs::checked_tensor_len's iterator try_fold used while loading checkpoint weight tensors is not modelled in Verus; exec_weight_layer_slice takes buf.len() == n_layers * per_layer and n_layers * per_layer <= usize::MAX as requires.
  4. The pos < seq_len guard is assumed, not proved. model.rs::State::forward's guard is read as a precondition of forward, and the proof is conditional on it.
  5. The debug_assert!s in ops.rs::attention are compiled out in release. They are not what makes the code safe. The safety argument is the composed arithmetic across exec_forward_cache_write_and_layer_slice and exec_attention_read: a layer slice is seq_len * kv_dim long, and pos < seq_len makes pos + 1 rows fit. That argument is machine-checked on the model, while the connection to the compiled src/ call site remains bounded by point 2.
  6. No float semantics whatsoever. dot, rmsnorm, rope, softmax, silu, matmul and the eight-accumulator reduction are not modelled, not reasoned about, and not verified. attention's arithmetic is treated as irrelevant to index safety, which it is, but that is a modelling decision, not a proof.
  7. forward -> attention composition (closed). Previously listed as an open manual step; exec_forward_cache_write_and_layer_slice now passes &key_cache[layer_start..layer_end] and &value_cache[layer_start..layer_end] directly into exec_attention_read, so Verus discharges the cross-function slice precondition directly.
  8. out and scores are modelled as &[f32], not &mut [f32]. The real signature is &mut [f32]. Writing to them cannot affect whether an index is in bounds, and Verus correctly refuses to carry s.len() across a loop iteration for a &mut, so mutability is genuinely dropped rather than proved irrelevant.
  9. Bounds safety does not catch wrong-but-in-bounds bugs. Mutant #3 (h / kv_mul -> h % n_kv_heads) is also in range and would sail through this proof. The differential test is what catches that one. Stating lemma_gqa_head_in_range is about totality of the mapping, not about it being the right mapping.
  10. Order of positions is not modelled. That positions must be fed 0, 1, 2, ... in order is a caller obligation (model.rs::State::forward@doc), not a checked precondition. A hole left by feeding position 7 before position 3 reads as zeros and is perfectly in bounds.
  11. Bounds safety is not memory safety. Nothing here covers use-after-free, aliasing, or anything the Rust compiler does not already cover.

4. Reproducing the check

Verus is not a dependency of this crate and is not vendored. It is obtained as a prebuilt release; cargo install vargo is not needed.

Linux x86_64 (matching CI)

# 1. Prebuilt Verus for Linux/x86_64 (~485 MB).
curl -fSL -o verus-x86-linux.zip \
  'https://github.com/verus-lang/verus/releases/download/release%2F0.2026.09.20.aef82ed/verus-0.2026.09.20.aef82ed-x86-linux.zip'
echo '7b870fa12bc589015c2fab60a8b3d9f07c7b1adb3444eb0fadffcbf7f0447b33  verus-x86-linux.zip' | sha256sum --check --strict -
unzip -q verus-x86-linux.zip -d verus-dist

# 2. Verus requires a matching rustc (1.98.1 for this release).
#    Using an isolated RUSTUP_HOME keeps your host toolchain untouched:
RUSTUP_HOME="$PWD/.verus-rustup" rustup toolchain install 1.98.1-x86_64-unknown-linux-gnu

# 3. Check citations (including self-test) and run Verus:
python3 verus/check_citations.py --self-test
python3 verus/check_citations.py
RUSTUP_HOME="$PWD/.verus-rustup" ./verus-dist/verus-x86-linux/verus \
  --crate-type lib --no-cheating verus/kv_cache_bounds.rs

macOS arm64

# 1. Prebuilt Verus for macOS/arm64 (449 MB).
curl -fSL -o verus-arm64-macos.zip \
  'https://github.com/verus-lang/verus/releases/download/release%2F0.2026.09.20.aef82ed/verus-0.2026.09.20.aef82ed-arm64-macos.zip'
echo '3f89fd250d1e9792ed6d0c7c3ad72c03c02fdbca3f0638987af6e153d69377bc  verus-arm64-macos.zip' | shasum -a 256 --check -
unzip -q verus-arm64-macos.zip -d verus-dist

# 2. Install the matching rustc into an isolated RUSTUP_HOME:
RUSTUP_HOME="$PWD/.verus-rustup" rustup toolchain install 1.98.1-aarch64-apple-darwin

# 3. Check citations and run Verus:
python3 verus/check_citations.py --self-test
python3 verus/check_citations.py
RUSTUP_HOME="$PWD/.verus-rustup" ./verus-dist/verus-arm64-macos/verus \
  --crate-type lib --no-cheating verus/kv_cache_bounds.rs

--crate-type lib is required because the file has no main. --no-cheating rejects assume, admit and external_body; the file uses none, and this flag makes that machine-checked rather than a promise in a comment.
